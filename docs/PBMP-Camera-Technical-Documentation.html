1. What the app is and why it exists

PBMP Camera is a web app that turns an ordinary phone or laptop camera into a sports analysis tool for tennis (and cricket), and adds a gym workout log. It runs entirely in the browser: nothing has to be installed. A small Node.js server keeps the shared data.

1.1 The problem it solves

• Professional ball-tracking and line-calling systems (like Hawk-Eye) need many expensive, fixed cameras. Clubs, coaches and players rarely have them.

• Coaches want to see, after practice, how high and fast a ball went, where it bounced, whether it was in, what shot a player played, and how the player moved.

• Footage is often filmed through a fence, from a shaking phone, or from an awkward angle.

1.2 What the app does

• Captures photos and videos from any camera the browser can open, and keeps them in a shared, private session.

• Understands the court: finds the court lines by itself (or from 3 or 4 clicked points), measures the court in meters, and works out where the camera stands and how it is tilted.

• Tracks the ball in recorded video and live, finds bounces, calls them IN or OUT for a chosen area (doubles, singles, a service box), and rebuilds the ball's 3D flight, height and speed from a single camera.

• Predicts where the ball would have gone after the video ends, with a physics engine (gravity, bounce, net, air drag, spin).

• Combines two phones recording at the same moment into a true 3D path.

• Follows the players: 17 joints each, a letter (A, B, C, D) that sticks to each person by the colors of their clothes, their racquet, their position on court, and how far they ran.

• Reads the match: each hit, who hit it, what stroke it was (serve, forehand/backhand drive or volley, smash), rallies, and the rests between points.

• Shows the match from any viewpoint (for example "10 feet behind the baseline, 15 feet up, on the right side"), even though the video was filmed from somewhere else.

• Fixes difficult footage: follows and steadies a moving camera, and paints out a chain-link fence.

• Logs workouts: exercises, sets, rest and interval timers, one-rep max (1RM) estimates and personal records.

• Builds training data for a custom AI model: label frames, export a YOLO dataset, or upload to Roboflow, then load the trained model back into the app.

1.3 Who it is for

Players, coaches, clubs and developers. Developers can also use the same server from Flutter, Android and iOS apps through the included Dart, Kotlin and Swift clients.

2. How the app was built

2.1 Approach

• Browser first. All camera access, AI and 3D math run in the user's browser. This keeps video private, works offline for capture, and keeps the server small and cheap.

• One language end to end. TypeScript is used for the app, the server, the shared data types and the tests, so a change to a data shape is checked everywhere at once (shared/contracts.ts).

• Few dependencies. Only 7 runtime npm packages. The server uses Node's built-in modules (http, sqlite, crypto, zlib) instead of a framework or database server. ZIP and tar archives, the multipart parser and the ONNX metadata reader are written in the project.

• Heavy parts load only when needed. Each screen is a separate bundle; MediaPipe, ONNX Runtime models, OpenCV.js, Rapier and Three.js load the first time a feature uses them.

• Work off the main thread. AI models run in a Web Worker (onnx.worker.ts) and the 3D flight fitting runs in another (flight.worker.ts), so the page stays smooth.

• Measured, not guessed. Every vision feature has tests with known geometry (a synthetic camera, court and ball), and the browser tests run the real app with a fake camera video.

2.2 Build steps in order

1. React + Vite + TypeScript app with the camera screen (getUserMedia, MediaRecorder).

2. MediaPipe object detection and pose; AI on/off, labels and skeleton.

3. Results screen; IndexedDB storage; then the Node server with SQLite and shared sessions.

4. Court calibration with OpenCV.js (top-down court), then ball tracking with YOLOv8n (ONNX Runtime Web).

5. Single-camera 3D flight fitting; Rapier physics prediction; Three.js views.

6. Synced multi-phone takes and triangulation; live ball with IN/OUT.

7. Custom models (upload or link), workouts, native clients, training pipeline.

8. Private sessions with keys, tests, CI, backup/restore, Docker deployment on Zeabur.

9. Limits fixed: more court lines and call areas, any 4 or 3 court points, drag and spin, 30 fps tracking, a smaller bundle, threads on Safari.

10. Camera angle, live xyz, feet/meters, multi-person pose (YOLOv8n-pose), virtual camera, camera motion and stabilization, automatic court finding, fence removal.

11. Player letters by clothes, court names, racquet tracking, shot types, rallies and rests.

3.2 How a request flows

1. The browser opens https://reactcamapp.zeabur.app. The server's serveApp sends index.html and the JavaScript bundles with COOP/COEP headers (cross-origin isolation, which lets WebAssembly use threads).

2. SessionProvider (src/session/SessionContext.tsx) asks POST /api/sessions to open or create a session. The server creates a 256-bit key, stores only its sha256 hash, and sets an HttpOnly cookie.

3. Every later API call carries that cookie (browsers) or an X-Session-Key header (native clients). handle() in server/index.ts finds which session the URL belongs to (owningSession) and checks the key before doing anything.

4. Captures are uploaded with POST /api/sessions/:id/assets (multipart). The server validates the details, writes the file to data/media/<id>, and the row to SQLite.

5. Analysis (ball, players, motion) runs in the browser. Its results (tracks) are saved with PUT /api/assets/:id/ball-track, pose-track or motion-track, so any device of the session sees them.

7. Features and how each one is built

Each feature lists what it does, how it works step by step (with the functions involved), the files, what is stored, and the APIs it calls. Function names match Appendix A.

7.1 Sessions, sharing and privacy

What it does. Every capture, court, track and workout belongs to a session. The link of a private session (with its key) opens it on another device; without the key the server refuses.

How it works.

1. SessionProvider (SessionContext.tsx) reads ?session= from the address (requestedSessionId) or the remembered id (rememberedSessionId), or makes a new UUID.

2. With a shared key in the link it calls unlockSession (POST /unlock); otherwise fetchSession or openSession (POST /api/sessions).

3. The server's newKey makes a random 256-bit key; only its sha256 is stored (setSessionKeyHash). rememberKey sets the HttpOnly cookie pbmp_key_<id>. The key is returned once and kept in localStorage only to build the share link (rememberSessionKey, shareLink).

4. On every request, handle() finds the owning session (owningSession) and canUseSession checks the cookie or X-Session-Key with keyMatches (constant-time). A wrong key gets 403, which the app shows as "This session is private. Open it with its full link".

5. After unlocking, the key is removed from the address bar (history.replaceState).

6. Older open sessions show "Make private" (lockSession, POST /lock).

7. If the server cannot be reached, the app works offline: captures go to IndexedDB (saveStored) and courts/tracks to localStorage; they upload when the server is back (syncLocal, syncBallTracks).

Files. src/session/SessionContext.tsx, api.ts, context.ts, db.ts; server/index.ts; server/store.ts. Stored. sessions table (key_hash), cookie, localStorage pbmp-session-id, pbmp-session-key:<id>, pbmp-device-id. APIs. POST /api/sessions, GET /api/sessions/:id, POST /unlock, POST /lock.

7.2 Camera explorer, photos and video

What it does. Opens any camera, shows its settings and supported ranges, takes photos and records videos.

How it works.

1. useCamera lists cameras (readCameras), opens the chosen one with getUserMedia, and describes it (describeTrack): label, resolution, frame rate, facing mode and their ranges.

2. Capture photo: jpegFromVideo grabs the frame (WebCodecs when available, else a canvas) as JPEG; the AI snapshot of that moment is attached (readSnapshot).

3. Recording: MediaRecorder with the best format (preferredMime). The start time is taken on the server's clock (serverNow) so takes from several phones line up.

4. addAsset saves the capture in the session (uploadAsset, POST /assets); if offline, in IndexedDB.

5. The device's cameras are reported once (saveCameras, PUT /cameras).

Files. src/camera/useCamera.ts, webcodecs.ts; src/pages/CameraExplorer.tsx. Stored. assets table and data/media/<id>; cameras table. APIs. POST /api/sessions/:id/assets, PUT /api/sessions/:id/cameras, GET /api/assets/:id/file.

7.3 Live AI: objects and skeletons

What it does. With AI on, the preview shows boxes and labels of objects and the skeleton of people.

How it works.

1. AiProvider (AiContext.tsx) loads MediaPipe (loadEngines: EfficientDet-Lite0 and Pose Landmarker Lite, GPU first, CPU as fallback) and, when chosen, an ONNX model (prepareOnnx) or YOLOv8n-pose (preparePeople).

2. useLiveAnalysis runs a loop on the preview: one pass for pose, one for objects, alternating, about every 160 ms (faster on quick devices).

3. Objects: MediaPipe readDetections, or ONNX detectSource in the worker (decodeYolo with non-maximum suppression).

4. Pose: MediaPipe readPose (one person, 33 points, 3D world pose), or YOLOv8n-pose detectPeople (every person, 17 joints) with players named by side (assignPlayers).

5. publish stores the snapshot; AnnotationCanvas draws it (drawAnnotations, drawPeople). The confidence slider hides low scores.

6. The ONNX worker picks the faster backend on the first model: WebGPU (skipping software adapters) or WASM with up to 4 threads (timeRun).

Files. src/vision/AiContext.tsx, engine.ts, useLiveAnalysis.ts, onnxDetector.ts, onnx.worker.ts, yolo.ts, models.ts, draw.ts; src/components/AiControls.tsx, AnnotationCanvas.tsx. Stored. The snapshot inside the photo's asset row (inference_json); settings in localStorage (pbmp-ai-enabled, pbmp-ai-confidence, pbmp-object-detector, pbmp-pose-mode).

7.4 Custom AI models

What it does. Load your own YOLOv8/YOLOv5 ONNX model (from a file or an https link), choose which classes are the ball, and use it for detection and ball tracking on every device of the session.

How it works.

1. ModelLibrary reads the file's metadata without running it (readOnnxMeta: class names, input size, shapes) and makes a draft (draftFrom).

2. Links are downloaded through the server (fetchModelBytes, GET /api/fetch-model), which only allows https, checks DNS, refuses private addresses (privateAddress) and limits the size (proxyModel).

3. Saved with uploadModel (POST /models); edited with saveModelDetails; deleted with deleteRemoteModel.

4. decodeYolo handles any class count and both tensor layouts.

Files. src/components/ModelLibrary.tsx, src/vision/onnxMeta.ts, models.ts; server/index.ts. Stored. custom_models table, file in data/media. APIs. POST /api/sessions/:id/models, GET/PUT/DELETE /api/custom-models/:id(/file), GET /api/fetch-model.

7.5 Court calibration (4 points, 3 points, landmarks, call areas, names)

What it does. Tells the app where the court is in a photo so everything can be measured in meters.

How it works.

1. The court screen (CourtPlane) offers tennis or cricket, "Points to click" sets (COURT_LANDMARKS and LANDMARK_SETS in shared/court.ts), each point, a court name and the call area.

2. Four points: courtHomography solves the 8 unknowns of the photo-to-court homography. landmarksProblem refuses points that are the same or lie on one line.

3. Three points with a level phone: levelCamera searches yaw, pitch and focal length (Levenberg-Marquardt, refineLevel); the camera position follows linearly. The fourth point is projected (completingLandmark) and saved as estimated (estimatedPoints). levelSpread shows how far it would move if each click were 1.5 px off; a warning appears when two cameras fit.

4. cameraFromCourt recovers the camera (focal, rotation, position) from the homography; cameraText shows "Camera at x ..., ... behind the near baseline, ... high, looking ... down".

5. renderCourt (OpenCV warpPerspective) flattens the photo and draws the court lines on it; the ankles of a MediaPipe pose are placed in meters.

6. lineCall decides IN/OUT for the chosen area (COURT_AREAS: doubles, singles, four service boxes, pitch); a ball touching a line is in.

7. The court is saved per device (saveRemoteCourt), so each phone of a session has its own.

Files. src/components/CourtPlane.tsx, CourtLinesOverlay.tsx; shared/court.ts; src/vision/flight.ts, cameraPose.ts, opencv.ts, court.ts, courtOverlay.ts. Stored. device_courts table (court_json); localStorage pbmp-court:<session>. APIs. PUT/DELETE /api/sessions/:id/court.

7.6 Automatic court finding

What it does. "Find the court automatically" places the court without any clicks.

How it works.

1. detectCourt (courtDetect.ts) scales the photo, and OpenCV's top-hat filter keeps thin bright things. A pixel is painted line when it is brighter than its surroundings, nearly white (not a yellow ball or a shirt), and near the brightest pixels of the picture (so gaps between dark fence wires do not count).

2. HoughLinesP finds straight segments; mergeSegments joins pieces of the same line.

3. fitCourtModel tries pairs of strong lines across and along the court against pairs of the court model's baselines/service lines and sidelines (homographyFrom), scores each court by how many of its line pixels are painted (scoreOf), rejects collapsed or folded courts (sensible), and penalizes painted lines it leaves unexplained (unexplained).

4. refine nudges the four corners; polish fits a straight line to the painted strip next to each court line and redoes the court through every crossing (sub-pixel).

5. canonical picks the mirror image where the near baseline is nearer the camera. landmarksInView returns four landmarks inside the photo.

Files. src/vision/courtDetect.ts, courtFit.ts. Accuracy (tests). Within 4 px from behind, the corner and high on the side, with a fence and players in the photos.

7.7 Units, camera angle and live xyz

• Units. The header's Units switch (setUnits, useUnits) changes every length to meters or feet and speeds to km/h or mph (length, speed, xyz).

• Camera angle. describeCamera gives position, pitch (down), yaw (turn) and roll; cameraText writes it.

• Origin. (0, 0, 0) is where the left doubles sideline meets the near baseline; x runs along the baseline, y toward the far baseline, z up. drawCourtOverlay draws the axes.

• Live xyz. On videos the 3D ball's coordinates are drawn next to it with a line down to its shadow (drawHeight). On the live camera, the last 3D fit carries the newest ball (carried in useLiveBall).

7.8 Ball tracking in a video

What it does. Finds the ball in every frame, links it into one path and marks bounces.

How it works.

1. trackBall opens the video off screen (openVideo) and seeks frame by frame at 10, 20 or 30 fps (seek).

2. Each frame goes to the ONNX worker (detectBall to detectSource) with the ball classes of the chosen model (sports ball for YOLOv8n).

3. linkBallTrack picks, frame by frame, the candidate nearest where the ball should be from its recent speed (nearestToPrediction), skipping decoys, and marks bounces where the ball turns around in the image.

4. The track is saved (saveRemoteBallTrack); BallOverlay draws the trail; BallCourtMap projects ground points to the top-down map (projectToCourt) with IN/OUT.

Files. src/vision/ballTracker.ts, ball.ts; src/components/BallTracking.tsx. Stored. ball_tracks table; localStorage pbmp-ball:<session>. APIs. PUT/DELETE /api/assets/:id/ball-track.

7.9 Single-camera 3D flight

What it does. Rebuilds the ball's 3D path from one camera: height, speed, bounce spot.

How it works.

1. The camera comes from the court (cameraFromCourt).

2. fitFlights splits the track where the ball was lost (splitOnGaps) and segments it into flights by dynamic programming: each flight is a gravity parabola and pays a penalty for its six unknowns; held or misdetected stretches can be set aside (segment, freeCost).

3. solveChain fits linked flights by least squares: continuous at each break, on the ground at bounces, with a soft bounce model (restitution 0.75 tennis, 0.55 cricket), reweighted by depth so residuals are pixels.

4. classifyBreaks decides bounce or hit at each break (bestBreak, bounceLike) and refinePairs tunes neighbouring breaks together.

5. continues rejoins a short far flight right after a bounce, which one camera cannot place on its own.

6. Each flight's height uncertainty (heightSigma) comes from the fit's normal matrix; flights that are uncertain or unphysical are listed but not drawn (plausible).

7. All of this runs in a Web Worker (flight.worker.ts, fitFlightsInWorker, sharedFlightFit).

Files. src/vision/flight.ts, flightFit.ts, flight.worker.ts, flightText.ts; src/components/BallFlight.tsx.

7.10 Physics prediction (Rapier)

predictFlight builds a Rapier world (ground, net or stumps), starts the ball with the last flight's position and velocity, and steps 240 times a second. Air drag (drag coefficient 0.55 tennis, 0.5 cricket; ball mass 57 g / 160 g) and Magnus lift from spin are applied each step (pushAir). Topspin and slice set a real spin, so the bounce kicks. The "Prediction physics" dropdown (AirSelect, air.ts) chooses drag, topspin, slice or none.

7.11 Live ball with IN/OUT

useLiveBall runs YOLOv8n on the preview as fast as the device allows, links a live track, marks candidate bounces, and every half second fits the last 4 seconds in the flight worker to confirm bounces in 3D. Calls use the phone's court and call area. LiveBallOverlay draws the trail, the IN/OUT marks, the court and the 3D coordinates. A recording made while live ball is on keeps the live track.

7.12 Synced takes and two-camera 3D

1. Every phone matches its clock to the server (syncClock: several round trips to /api/time, the fastest wins).

2. Start synced take (useSyncedTake, createTake) asks the server for a start time 2.5 s ahead; other phones poll takes/latest and record at that moment.

3. triangulateTake places each camera from its own court, finds the small clock error between them (bestShift, up to 0.3 s), intersects their rays into 3D points, and finds bounces where the path meets the ground (lowPoints).

Files. src/camera/useSyncedTake.ts, src/session/clock.ts, src/vision/triangulate.ts, src/components/TakePanel.tsx. Stored. takes table; assets keep take_id and started_at. APIs. GET /api/time, POST /takes, GET /takes/latest.

7.13 Camera motion and stabilization

1. trackMotion matches each sampled frame to the court photo with OpenCV ORB features (MotionMatcher), first on the ground around the court (groundMask), then anywhere.

2. Matches are checked both ways (pairs). estimate finds a two-point similarity (shift, turn, zoom) by RANSAC, refuses inliers that lie along one line (spreadsOut), upgrades to a full homography when inliers spread across the view, and keeps the last motion (or no motion) when it explains the frame as well.

3. Frames that do not match keep the last good motion; the summary shows the largest shift and turn and how many frames matched (motionSummary).

4. VideoCourtOverlay carries the court lines with the camera (movedCourt). SteadyFrame warps the whole frame back with a CSS matrix3d (cssMatrix).

5. steadyBallTrack and steadyPoseTrack take the motion out of the tracks before fitting, mapping, line calls, the match, the virtual camera and triangulation.

Files. src/vision/motionTracker.ts, motion.ts; src/components/MotionPanel.tsx. Stored. motion_tracks table. APIs. PUT/DELETE /api/assets/:id/motion-track.

7.14 Fence removal

FenceRemover finds thin dark wires with OpenCV's black-hat filter, measured against local brightness (so wires over shade count). Across 16 frames (learnFence), only pixels that are wire in most frames stay; they must line up into long straight runs along the fence's two main directions (Hough lines, carried to the edges), so windows, leaves and shadows are left alone. clean paints the wires out from their surroundings (cv.inpaint, Telea). FenceCanvas shows the cleaned video, the mask or the original. Tracking keeps using the recorded frames, because the pose model sees through a thin fence better than through filled-in pixels.

7.15 Players: multi-person pose, letters, racquets, positions

1. trackPlayers reads the video, runs YOLOv8n-pose (detectPeople, decodeYoloPose) for every person's 17 joints, and names the near and far players by the side of the net their feet stand on (assignPlayers, feetOnCourt), leaving out people far off the court (umpire, spectators).

2. YOLOv8n's "tennis racket" class finds racquets; holdRackets gives each to the player whose wrist is nearest and notes the hand.

3. appearanceOf builds shirt and shorts color histograms; PlayerIdentifier gives each person a letter (A, B, C, D) by colors and last position, keeps it through occlusions, learns only from clear looks, and carries letters to other videos of the session (seeds).

4. playerPaths measures distance run and time at the baseline, mid-court and net (courtZone). PositionMap draws positions and trails on the top-down court. jointAngles gives knee, elbow and hip angles.

Files. src/vision/playerTracker.ts, players.ts, identity.ts, yolo.ts; src/components/PlayersPanel.tsx. Stored. pose_tracks table (frames and player profiles). APIs. PUT/DELETE /api/assets/:id/pose-track.

7.16 Match reading: shots, rallies, rests

1. findHits finds hits where the ball changes flight without touching the ground (and at the first flight).

2. The hitter is the player in that half nearest the ball; their joints are lifted to 3D (liftPoint).

3. classify names the stroke: hand above the head after a pause from the baseline is a serve, otherwise a smash; the racquet's side of the body facing the net with the dominant hand (racketHands) gives forehand or backhand; no bounce since the other player's hit makes a volley, else a drive; both wrists together on the backhand side is two-handed.

4. handSpeed gives the hitting hand's speed. readMatch groups shots into rallies (gaps under 4 s) and marks quiet stretches of 6 s or more as between points and 60 s or more as breaks, noting when players were resting.

5. MatchPanel draws the timeline (rallies, rests, shot markers) and lists; clicking seeks the video.

Files. src/vision/match.ts; src/components/MatchPanel.tsx.

7.17 Virtual camera

parseViewCommand reads "10 feet behind the baseline, 15 feet above, right side" (Hinglish words like peeche/upar also work; lengths without units use the header's units). viewPose turns it into a camera position looking at the court's center. VirtualView renders with Three.js: the ground uses a shader that looks up each ground point's pixel in the current video frame through the homography (and the camera motion), so the real court appears from the new angle; players are stood up from their 2D joints on an upright plane through their feet (liftPerson); the ball follows its 3D flight. Presets: real camera, umpire's chair, overhead.

7.18 Workouts

WorkoutProvider keeps workouts in localStorage first (offline) and syncs each change to the server with last-write-wins (putWorkout, removeWorkoutRemote; deleted workouts become tombstones). WorkoutLog runs a workout (ExercisePicker, SetRow, rest timer), WorkoutHistory lists finished ones with records (recordsFor), OneRepMaxView estimates 1RM (Epley, Brzycki, Lombardi), and WorkoutTimers has interval timers and a stopwatch (phaseAt, beep).

Stored. workouts and exercises tables; localStorage pbmp-workouts:<session>. APIs. GET /workouts, PUT/DELETE /workouts/:id, PUT/DELETE /exercises/:slug.

7.19 Training pipeline

The Training screen saves class names (saveClasses), adds frames from photos or videos (photoFrame, sampleFrames, uploadTrainingImage), labels them in the Labeler (draw boxes, number keys for classes, Suggest boxes from AI with suggestBoxes), and exports a YOLO dataset ZIP (server: yoloLabel, dataYaml, vocXml, zip) with a train.py that trains with Ultralytics and exports ONNX. Or it uploads to Roboflow (uploadToRoboflow: image, then Pascal VOC XML).

Stored. training_sets and training_images tables; JPEGs in data/media. APIs. GET /training, PUT /training/classes, POST /training/images, PUT/DELETE /api/training-images/:id, GET /training/export, POST /training/roboflow.

7.20 Admin: stats, backup, restore

With ADMIN_TOKEN set on the server, GET /api/admin/stats counts the data, GET /api/admin/backup streams a tar.gz of a consistent SQLite snapshot (VACUUM INTO) plus all media, and POST /api/admin/restore unpacks a backup into an empty server only (untarGzip, applyRestore).

8. The backend in detail

8.1 Start-up

server/index.ts calls openStore (server/store.ts): it opens or creates data/pbmp.sqlite inside PBMP_DATA_DIR (default server/data), creates the media folder, creates missing tables and runs migrations (migrate). Then createServer(handle) listens on PORT / PBMP_PORT (default 8787 in development, 8080 in Docker).

8.2 Routing and order of checks

1. OPTIONS requests get CORS headers (cors) for the native clients.

2. Public routes: /api/health, /api/time, /api/models, POST /api/sessions, POST /unlock.

3. Admin routes check Authorization: Bearer ADMIN_TOKEN (adminAllowed).

4. Every other /api route: owningSession works out which session the URL belongs to (directly, through an asset, a custom model or a training image); canUseSession checks the key. Without it: 403 "This session is private. Open it with its full link."

5. The route validates its input (the as... functions), calls the store, and replies with sendJson.

6. Anything not under /api is the app (serveApp): files from dist with long caching for hashed assets, index.html for screen routes, COOP same-origin and COEP require-corp.

8.3 Security

• Session keys are 256 random bits; only sha256 hashes are stored; comparison is constant-time.

• The key travels in an HttpOnly, SameSite=Lax cookie (Secure behind https), or the X-Session-Key header.

• Every input is validated with strict limits (sizes, ranges, UUIDs, class names). JSON bodies are limited to 1 MB (4 MB for ball and motion tracks, 12 MB for pose tracks). Models up to 200 MB, training images up to 20 MB.

• The model-link proxy allows only https, resolves DNS first and refuses private, loopback and link-local addresses, and limits the size.

• Restore only works on an empty server, and archive paths are checked.

8.4 Files and streaming

Uploaded files are written to data/media/<id>. GET /api/assets/:id/file supports HTTP Range requests (206 Partial Content), so videos can be scrubbed.

13. Deployment and operations

• Zeabur builds the Dockerfile from the GitHub main branch on every push. The service listens on 8080, the domain reactcamapp.zeabur.app points to it, and the volume /src/server/data keeps the database and media across deploys. ADMIN_TOKEN is set as a variable.

• Other hosts. railway.json, fly.toml and deploy/vps (Docker Compose with Caddy for https) are ready. Move data with GET /api/admin/backup on the old host and POST /api/admin/restore on the new one (deploy/README.md).

• Image. Stage 1 (node:22.21.0-slim) installs packages and runs npm run build; stage 2 copies dist and the compiled server and runs node server/index.js.

Appendix E: Glossary

TermMeaning
HomographyA 3x3 matrix that maps points on a flat surface (the court) from one view to another (the photo)
CalibrationTelling the app where the court is in a photo
LandmarkA known court point (a corner, a service line end, the T)
Call areaThe part of the court that counts as in
TrackResults stored per video: ball points, player poses, or camera motion
FlightOne stretch of the ball's path between bounces or hits, a gravity parabola
RestitutionHow much of its vertical speed a ball keeps after a bounce
Magnus liftThe sideways or downward push spin gives a ball in the air
TriangulationFinding a 3D point from two cameras' rays
ORBA fast image feature detector and descriptor in OpenCV
RANSACFitting a model while ignoring wrong matches by trying random small samples
Top-hat / black-hatImage filters that keep thin bright / thin dark details
InpaintingFilling masked pixels from their surroundings
ONNXA standard file format for trained AI models
YOLOA family of fast object detection models (You Only Look Once)
WebGPU / WASMWays to run fast code in a browser: on the graphics card / as compiled WebAssembly
COOP / COEPHeaders that isolate the page so WebAssembly can use threads
Session keyThe secret in a private session's link
TombstoneA record that something was deleted, so other devices delete it too
